**Findings:** **R5** the engine's PDF names its OCGs after the internal layers (`CUT`…) and its perforation swatch `Perforation`; Illustrator users see `CutContour` only as a swatch. The designer PDF names layer **and** swatch the same (`Perf` for both, as the prompt lists). **R6** the store keeps `store.conversations.get|messages|send` (singular `/conversation`, B4.6): they keep working on the customer's support thread, the new thread endpoints are added beside them (additive, contract rule). **R7** conversations' first-response SLA exists only on support tickets; D-221's 1 business day applies to every CS conversation (the decision opens a CS conversation for each ticket).

**Proposed decisions (conservative; reversible by a new decision):**
- **D-297 Launchpad** — one read for the signed-in home: up to 5 designs (own and the companies' the customer may order for, latest change first), up to 5 reorder candidates (open suggestions, soonest first, then delivered orders offering `order.reorder`), the orders and order groups needing the customer (`pay`, `approve_proof`, `upload_artwork`, `confirm_receipt`) with that next action and its deep path, and one recommended next step by a fixed order: pay → approve proof → upload artwork → confirm receipt → due reorder → resume the latest design → start a configuration. Computed on read, nothing stored.
- **D-298 Defaults** — read only: the default (else last used) delivery address, the default tax profile, per product type the material and print method of the customer's latest quotation of that type, and per company the customer may order for whether it has an active brand kit. Nothing is pre-filled server-side; the web uses the values.
- **D-299 Deep links** — a notification to a user with a page for the event gets `{{link}}`: `<web>/l/<token>`, a random token stored as SHA-256, bound to that recipient and that one path, valid `notifications.deep_link_ttl_hours` (proposed **72**, Superadmin). Resolving it never signs anyone in: it returns the zone and path; a signed-in caller who is not the recipient gets 404, an expired token 410.
- **D-300 Conversations v2** — threads per customer × subject (`support` (the general chat), `order`, `design`, `rfq`, `rfq_basket`), one live per pair; company recorded from the subject; participants with read positions; attachments through the files module; context cards to the customer's own order / design / rfq / quotation; internal notes (staff only, never pushed); canned responses (CS Lead, `conversations.manage_canned`, audited); SLA: first response due = first inbound + `support.first_response_business_days` (D-221), resolution due from `conversations.resolution_business_days` (defined **unset**, CS Lead — no target until set); LINE: a linked account's messages go to the customer's live support thread and a live LINE thread merges into it on link; staff replies go to LINE when the thread's `reply_channel` is `line` (the customer sets it; default the channel of their last inbound message).
- **D-301 RFQ basket** — a draft basket of up to 20 items (technical limit), each a product type + RFQ spec snapshot (the store RFQ form, D-183 millimetres) + optional design version; one submission validates every item and creates one RFQ per item (same delivery postcode, target date, channel) in one transaction, plus the basket's conversation; each item is quoted, consulted and accepted exactly like an RFQ; `acceptItems` accepts the chosen quotation tier of each item and adds the resulting quotations to the cart at the quoted price, locked until the quotation's validity.
- **D-302 Designer PDF** — every `pdf` dieline download is the designer PDF: one optional-content layer and one spot swatch each named `CutContour`, `Crease`, `Perf`, `Glue`, `Bleed`, `Safe` (+ `HalfCut` only when the style has half-cuts), bleed and safe distances from `artwork.preflight_rules`, title `<style code> <name> <L×W×H> mm (<basis>)`, the style code in the Info dictionary (`Subject`, `Keywords`, `PackioStyleCode`) and in XMP; SVG and DXF unchanged.
- **D-303 Journey analytics** — journeys = the scorecard tasks with a web flow (discovery → price, studio, checks, order, sample, target price, tracking, reorder, claim, documents, dieline, partner job), each an ordered list of steps matched by event; a generic closed-schema `journey_step` event for steps no existing event covers; daily facts per journey / step (consented sessions); a weekly comparison (Monday, Bangkok) of the last 7 days' first-to-last conversion against the 7 before raises ops signal `journey_conversion_drops` when it fell by more than `analytics.journey_drop_alert_pct` (**15**, from `docs/ux/competitive-scorecard.md` §4) with at least `analytics.journey_alert_min_sessions` (proposed **30**) sessions in both weeks; the scorecard export is aggregates only with cells under `analytics.prospectus_min_group_size` suppressed.

**Assumptions:** (1) "Single-purpose" deep links are bound to one recipient and one screen, valid for repeated opens until expiry, never a sign-in (a sign-in link would be a credential, PDPA / ADR-0004). (2) Company members other than the thread's customer are not participants (the customer opened it; company-wide inboxes are not asked for). (3) A context card is a reference (type + public id) the API resolves on read for the reader — never a copy of prices. (4) Journey steps are counted per consented session (D-102 consent mode), like the studio funnel. (5) The basket is per customer and channel `web`; CS creates RFQs one by one as today.

**Plan (one release per deliverable, merge to `main` at the end):** **B1** a launchpad · b defaults · c deep links → `v0.32.0`. **B2** a schema + subjects + participants · b attachments, context cards, notes, canned responses · c LINE merge + reply channel · d inbox filters, SLA, stats, ops signal, customer route → `v0.33.0`. **B3** baskets → `v0.34.0`. **B4** designer PDF → `v0.35.0`. **B6** journeys, alerts, export → `v0.36.0`.
